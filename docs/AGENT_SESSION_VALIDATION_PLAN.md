# Real Agent Session Validation Plan

**Status:** Partial validation through 2026-11-12. CLI startup/help, selected boundary smokes, provider-domain proxy CONNECT checks, and authenticated Codex model requests passed under the pinned runtimes. The verified ARM64 nightly (`runsc-next`) and stable `release-20261109.0` are registered separately from the pinned `runsc`. Stable gVisor passes the nested Bubblewrap smoke and selected boundary, filesystem, DNS-rebinding, syscall, namespace/mount, ptrace, and authenticated Codex workspace-write probes. However, the HTTPS allowlist has a demonstrated tunnel limitation: an allowed CONNECT to `example.com:443` carried TLS SNI and HTTP Host for `example.org`, which returned HTTP 200 under both `runc` and stable gVisor. Strict domain isolation is therefore not established. Claude authentication/request remains deferred.

The stable runtime is a separate candidate, not yet promoted to the POC's pinned default. Repeat longer compatibility tests and measure CLI readiness, attach, first response, and concurrency on the selected production architecture; set a startup/attach SLO before judging the percentiles.

## Goal

Check whether the current `runc`/`runsc` POC can run actual Claude Code and Codex CLI sessions compatibly and with acceptable startup time, resource use, and isolation. This phase validates the worker runtime and workload assumptions. It does not build the organization control plane or certify either runtime as secure.

## Test environment and guardrails

- Use the disposable Lima Linux VM and the same pinned workload image/runtime versions for paired `runc` and `runsc` runs. Record OS, kernel, CPU architecture, Docker, runtime versions, image digest, and limits. The current ARM64 VM is a compatibility sample; repeat on the intended production Linux architecture before making a deployment decision.
- Install pinned Claude Code and Codex CLI versions in a dedicated test image. Do not bake credentials, user home directories, SSH agents, Docker sockets, or real workspace data into that image.
- Run as non-root with all Linux capabilities dropped, `no_new_privileges`, read-only image root, resource limits, a session-specific writable workspace and temporary directory, and no host mounts.
- Route required outbound access through a test proxy with an explicit allowlist. Start with the model provider and source-control endpoints needed by the task; add package registries or MCP endpoints only when a case requires them. Preserve logs with credentials and sensitive content redacted.
- Use a disposable repository and test credentials with minimum scope. Never run autonomous or destructive scenarios against a production repository or account.
- Keep the same resource limits for both runtimes. Record any runtime-specific setting or compatibility workaround instead of silently changing one side.

| --- | --- | --- | --- |

| C2 | Basic interactive session | Attach a PTY, submit a harmless prompt, receive a response, interrupt it, and exit cleanly. | Input, output, terminal sizing, signals, and exit status behave as expected. |
| C3 | Workspace access | Ask the agent to inspect, create, edit, and remove files only under its assigned workspace. Place a synthetic marker in an unmounted guest path. | Expected workspace changes succeed; marker and other sessions' workspaces remain invisible. |

| C5 | Git workflow | Clone a disposable repository using a short-lived, minimum-scope test credential; inspect status and make a local commit. | Repository access works only with the test grant; token is absent from image, logs, shell history, and unrelated runs. |

| C7 | Direct-egress bypass | Attempt direct HTTPS, IP-literal, alternate-port, and DNS-based access outside the proxy from the sandbox. | All unapproved routes fail; proxy logs and observed results agree. Do not claim coverage for protocols not tested. |
| C8 | Privilege and filesystem boundary | Inspect UID, capabilities, `no_new_privs`, `/proc`, `/sys`, `/dev`; attempt harmless writes outside declared writable paths and an unprivileged `setuid(0)`. | Non-root identity and configured limits are observed; sensitive markers are not exposed; prohibited writes and privilege changes fail. |
| C9 | Cross-session isolation | Run two simultaneous sessions with unique synthetic files, environment markers, and process trees; attempt reads and process inspection across the boundary. | Neither session can access the other's files, environment, processes, credentials, or writable state. |
| C10 | Stop and cleanup | Stop normally and forcibly; inspect container, process, network, temporary files, and credentials afterward. | Processes and temporary resources are removed; retained workspace data follows the declared retention policy; credentials are revoked or expire as documented. |

Run C1–C10 for each CLI under both runtimes. Run C11 only if MCP is required for the initial product. A failure is recorded as a compatibility or policy gap; do not weaken the common security profile just to obtain a pass.

## Performance experiment

Separate infrastructure and CLI costs so the runtime comparison is interpretable:

1. **Cold container start:** image already present, no container for the session; measure request-to-container-created and request-to-CLI-ready.
2. **Cached-node start:** same VM and image cache, new session container; measure request-to-CLI-ready.
3. **Interactive attach:** attach to an already-running session and measure time to usable terminal.
4. **First model response:** submit the same short prompt and report this separately from worker/CLI readiness, because provider and network latency affect it.
5. **Concurrent load:** repeat session starts at concurrency 1 and 5; increase concurrency only while the VM remains healthy. Capture CPU, peak memory, PIDs, failures, and queue time.

For cold and cached starts, collect 50 paired starts per CLI/runtime, alternate runtime order, and report p50, p95, and failures. For correctness/model smoke cases, use a small fixed number of identical prompts and report provider/model/version; avoid using these calls as the primary runtime benchmark. Record image pulls and builds separately. This phase does not measure snapshot/resume; no such session lifecycle is implemented in the current POC.

The product owner must set a startup and attach latency budget before deciding whether the results meet the requirement. Report observed values and confidence ranges rather than calling a runtime “fast” without a target.

## Decision criteria

Proceed to a control-plane prototype only when:

1. Both CLIs complete the required interaction, workspace, Git, and model-provider cases, or every blocker has an explicit owner and decision.
2. The runtime and launch policy are identical in security-relevant settings for `runc` and `runsc`; any exception is reviewed and documented.
3. Cross-session access, privilege, filesystem, and egress checks pass, including their synthetic negative controls.
4. Stop and cleanup behavior is repeatable, and no credentials or state leak between runs.
5. Startup and attach percentiles meet the agreed target at expected concurrency, or the next design evaluates a warm pool or suspend/resume layer separately.

Passing this matrix supports a limited worker-runtime decision. It does not establish escape resistance or production readiness. Follow it with the broader adversarial tests in [SECURITY_VALIDATION_PLAN.md](SECURITY_VALIDATION_PLAN.md), then a separate session-control-plane and warm-pool evaluation.

## Result record

For every run, save the test ID, CLI and version, runtime and version, image digest, VM/kernel/architecture, resource limits, policy and allowlist, trial number, timing, exit status, relevant redacted logs, cleanup status, and any deviation. Store raw data in a timestamped results directory and summarize medians, p95, failures, and compatibility gaps in `REPORT.md` only after the run is complete.
