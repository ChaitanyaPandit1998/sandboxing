# Wardyn Fit Assessment

**Assessment date:** 2026-11-12
**Wardyn source reviewed:** local checkout `a60890b1e` (2026-11-05), version `0.10.0-rc.13`
**Assessment type:** source and documentation review plus a disposable local runtime/session smoke. No model call, credential flow, workspace persistence, SSO, production deployment, or load test was exercised.

## Summary

Wardyn's current source describes a broad session-governance control plane that overlaps substantially with the platform layer proposed for this POC: users and roles, policy-driven run creation, workspace handling, egress proxying, approvals, credential brokering, audit, attach, and stop/kill flows. The POC's comparative value is its independent, evidence-backed validation of the Codex container and `runsc-next` behavior in the Lima VM.

**Provisional direction:** evaluate Wardyn as the control plane and retain the POC regression suite as a worker/runtime acceptance suite. Do not start duplicating Wardyn's control-plane capabilities before the live compatibility checks below. This is not an adoption or production-readiness approval: Wardyn labels itself pre-alpha and says not to run production workloads.

## Key compatibility risk: Codex authentication

The POC currently demonstrates Codex using a device-login session inside a temporary user home. Wardyn's reviewed model-provider documentation describes OpenAI API-key injection for Codex and documents a separate Claude subscription sign-in flow. I found no source evidence in this checkout that the exact Codex device-auth / ChatGPT subscription session used by the POC can be connected as a Wardyn-managed provider.

Before adopting Wardyn for this use case, test the desired supported credential path with a test account. If the organization requires subscription/device authentication, treat it as a product requirement and obtain a supported design from the Wardyn maintainers or plan a scoped integration. Keep the current per-session home ephemeral while testing.

## Remaining live validation checklist

The following remain for a disposable Wardyn stack and synthetic workspace/test credentials:

1. **Partial:** the Docker runner resolved CC2 to `runsc-next` and the created container used that runtime. Repeat with the approved image digest and the final production-equivalent policy.
2. **Partial:** an interactive Codex container reached `RUNNING`, but its writable root, 1 GiB memory limit, and 512 PID limit differed from the POC baseline; no workspace was mounted. Match the approved limits and test declared-workspace access and persistence.
3. **Open:** confirm whether the supported Codex credential works; verify no provider token or login state appears in the image, logs, audit, or another session.
4. **Partial:** basic proxy egress denial, allowlisted-host routing, and cross-session `/tmp` separation were checked. Run the POC filesystem/privilege, egress-bypass, IP-literal, alternate-port, redirect, DNS-rebinding, and syscall compatibility cases through Wardyn.
5. **Partial:** synthetic approval, denial, audit, run kill, and normal container removal were demonstrated. Still test retry after decisions, timeouts, worker restart, OIDC actor attribution, revocation after failures, and audit-store tamper resistance.
6. **Open:** measure request-to-session-ready, attach-to-terminal-ready, first provider response, and cleanup at concurrency 1 and the agreed pilot concurrency.

**Promotion criterion:** all required identity, runtime, credential, network, workspace, cleanup, and audit behaviors pass for the exact deployed versions, or documented gaps are accepted by named owners. A passing matrix is scoped evidence; it is not a security certification.

## Live validation status

The disposable local stack ran on the existing ARM64 Lima VM with Docker 29.9.3. Wardyn `0.10.0-rc.13` used its published `wardyn/agent-codex-cli:local` image, which contained Codex CLI `0.149.1`; the POC image uses Codex CLI `0.167.1`. A temporary Compose override mapped CC2 to `runsc-next`, and Docker inspect confirmed the created Codex container used that runtime. The agent ran as UID 1000, with zero effective capabilities, `no_new_privileges=1`, an internal per-run network, and no mounts. Its root filesystem was writable, memory limit was 1 GiB, and PID limit was 512, so these settings do not match the POC's read-only root, 256 MiB, and 128 PID baseline.

One session ran `codex --version`; no provider was configured and no model request or Codex device login was attempted. From the sandbox, direct external access failed DNS resolution, the allowlisted OpenAI endpoint returned HTTP 401 through the Wardyn proxy without credentials, and an unlisted host was denied with HTTP 403. A synthetic `/tmp` marker written in one session was absent from the second session. In a separate disposable run, two synthetic unlisted-domain requests created pending egress approvals; approving one and denying the other changed their states as expected. The audit CLI returned `run.create`, `run.interactive.start`, `egress.hold`, both `approval.decide` events, `identity.revoke`, and `run.kill`. The decision rows identified the local admin token as a system actor, so human OIDC attribution remains untested. Wardyn reported the run as `KILLED` and removed its agent and proxy containers. SSO, workspace persistence, worker-restart cleanup, model credentials, and comparative latency/concurrency remain unverified. The temporary Wardyn sessions, stack, database volumes, source copy, and Compose override were removed; the two pre-existing agent sessions were left untouched. Published Wardyn images remain cached in the VM.
